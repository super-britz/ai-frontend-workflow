# 项目 AI 开发规则

## 协作偏好

- 使用中文沟通。
- 修改前先阅读现有实现、项目文档和相关测试。
- 保持改动聚焦，不扩大无关重构范围。
- 不覆盖用户已有改动；遇到冲突先说明。
- git commit 不添加 `Co-Authored-By` 或任何暴露 AI 辅助生成身份的信息。

## 前端实现规则

- 优先复用现有页面、组件、hooks/composables、services、types 和工具函数。
- 新增 UI 前先搜索已有组件和相似实现。
- 页面逻辑、业务组件、基础组件、接口请求、类型定义保持清晰边界；边界不清时先按已有相似实现处理，并记录待沉淀点。
- 不随意修改全局样式、主题变量、构建配置、路由结构或公共 API。
- 避免为了单个需求引入新的 UI 库、状态库、日期库或请求库。

## 组件库优先规则

- 基础 UI 默认使用项目现有组件库。
- 不手写已有组件库覆盖的按钮、表单、弹窗、抽屉、表格、分页、上传、通知、菜单、Tab、Tooltip。
- 组件库能力不足时，优先使用轻量局部组合；当复用、复杂状态或统一交互已经出现时，再沉淀项目级业务组件。
- 新增组件必须说明为什么现有组件无法满足，并补充使用示例或测试；不要在初始化或单个页面中提前设计完整业务组件体系。

## 样式与设计 Token

- 样式优先使用项目已有 token、主题变量、工具类或样式约定。
- 不硬编码可复用颜色、字号、间距、圆角、阴影和层级。
- 不通过局部 hack 覆盖组件库内部结构，除非项目已有明确模式。
- UI 文案、按钮、表单项和状态提示必须在移动端和桌面端不溢出、不重叠。

## 需求级事实文件

- PRD / Wiki / 产品说明使用 `frontend-product-requirements`，不要在聊天里隐式沉淀产品规则。
- Figma / 设计需求使用 `frontend-design-requirements`，不要在项目级规则里记录需求细节。
- 接口需求使用 `frontend-api-requirements`，不要根据 UI 猜接口字段。
- 产品、UI/设计和接口对齐使用 `frontend-alignment-requirements`，未决问题必须进入对应事实文件或决策文件。
- 启用 OpenSpec 时，需求级事实写入 `openspec/changes/<change-id>/docs/*` 和 `decisions.md`。
- 未启用 OpenSpec 时，可使用 `docs/ai/*-requirements.md` 作为轻量 fallback。

## 测试与验收

- 前端改动后运行项目可用的 lint、typecheck、test、build。
- 新增业务逻辑优先补单元测试。
- 新增组件或页面状态优先补组件测试或关键路径 E2E。
- 有 Playwright/Cypress 时，对核心页面状态做截图或 E2E 验收。
- UI 验收使用 `frontend-visual-verification`，前端专项 Review 使用 `frontend-code-review`。
- 无法运行的命令必须在最终回复里说明原因。

## Review 检查

- 是否复用了现有组件和样式系统。
- 是否遗漏 loading、empty、error、permission、disabled 等状态。
- 是否破坏响应式、可访问性、键盘操作或表单校验。
- 是否引入重复组件、重复请求逻辑、重复类型定义。
- 是否修改了无关全局配置或扩大了重构范围。

## 禁止事项

- 不为了快速还原视觉而绕过组件库。
- 不为了“显得规范”提前抽象不存在稳定复用场景的业务组件。
- 不把 mock 数据、调试代码、临时日志留在生产路径。
- 不在没有需求的情况下新增依赖。
- 不删除或回滚用户未要求处理的改动。
- 不提交未验证的 UI 改动。
